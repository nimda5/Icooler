# simulator

Виртуальные кулеры с платой связи по временному кадру §7.3 (SIM, §4.4): тот же протокол, что у прошивки, —
кадры, события, heartbeat, `hello`, `ack` и результаты команд. На нём Платформа работает, не дожидаясь устройства,
и на нём же идёт нагрузочный тест на 2 000 устройств (§6.1).

Дорожка: **Устройство**. ТЗ — [`doc/STAGE1_SPEC.md`](../doc/STAGE1_SPEC.md), §3.1, §4.4 (SIM), §7.3, FW-5, FW-10.
Каждое сообщение симулятора в тестах проверяется по схемам [`contracts/`](../contracts/README.md).

## Запуск

Node.js 24 запускает TypeScript напрямую, сборка не нужна.

```
pnpm install
cd simulator
node src/cli.ts --help
```

**Без хаба** — виртуальное время, прогон с максимальной скоростью, итог в JSON:

```
node src/cli.ts --devices 2000 --duration 1d
node src/cli.ts --devices 50 --duration 2d --scenario lte_loss=0.2 --scenario cooling_failure=0.05 --out messages.jsonl
```

**Azure IoT Hub** — реальное время, MQTT поверх TLS (порт 8883):

```
node src/cli.ts --transport iothub --host venden-iot-neu.azure-devices.net --auth x509 --certs ./certs --devices 10 --duration 2h
```

- `--auth x509` — в папке `--certs` на каждое устройство `<device_id>.pem` и `<device_id>.key` (выпуск — `provisioning`, CERT);
- `--auth sas --keys keys.json` — только для разработки на своём хабе, пока нет DPS и сертификатов: в ТЗ устройства подключаются только по X.509 (V-032);
- регистрация через DPS — после `provisioning`; сейчас устройства должны уже быть в реестре хаба.

Тип сообщения — свойство `mt` в теме D2C (`devices/{id}/messages/events/mt=frame&…`), команды — из
`devices/{id}/messages/devicebound/#`.

## Сценарии (SIM)

`--scenario <имя>=<доля устройств>`; момент начала — случайный в пределах прогона.

| Сценарий | Что происходит |
|---|---|
| `offline` | обрыв питания на 30 мин, затем старт с `reboot` (`power`) |
| `lte_loss` | потеря LTE на 2 ч: кадры и события в буфере, после восстановления — `hello` и досылка по порядку `seq` |
| `cooling_failure`, `heating_failure` | охлаждение/нагрев включены, а температура уходит от уставки |
| `filter` | ресурс фильтра почти исчерпан → `B1` |
| `consumption` | расход воды ×8 |
| `controller_silent` | контроллер не шлёт `AT+LOAD` 1 ч: `controller_not_confirmed`, кадр со старыми данными |
| `co2_out` | нет CO2 2 ч → `B3` (модель с газированной водой) |
| `local_schedule` | расписание изменено через Bluetooth → `schedule_applied` с источником `local` |
| `reboot` | перезагрузка по сторожевому таймеру |

Команды шлёт платформа (`dispatcher`); устройство исполняет их по жизненному циклу §7.3:
- хранит последние 100 `cmd_id`: повтор — тот же `ack` и результат, у `GET all` — тот же кадр;
- результат, доставка которого не подтверждена (в том числе `interrupted by reboot`), досылает при подключении —
  после `ack` платформа команду не повторяет (п. 3);
- проверяет `deadline_at`; у `hottank`/`coldtank`/`power` отдаёт `applied` и ждёт свежего `AT+LOAD` с нужным
  состоянием до срока: `controller_confirmed` с `uart_ms` или `controller_not_confirmed`;
- расписание принимает последовательностью `timezone` → `autopowerscheduling` → `schedversion` с проверкой CRC32.

Кадры и события уходят из буфера только по подтверждению доставки (PUBACK, QoS 1); неподтверждённые после обрыва
досылаются, повтор платформа отбрасывает по `seq` (FW-5).

## Что симулятор решает сам (нет в ТЗ — на согласование)

1. **`applied`, когда состояние уже нужное.** Например, `hottank:1` при уже включённом нагреве: `AT+PUSH` не шлётся,
   ответ — `applied: "pushed"`, подтверждение — по проверке `AT+LOAD` (`uart_ms` от проверки, как в §7.3 п. 8).
   `flag_only` — только когда включить сейчас нельзя (питание, окно, выходной).
2. **`GET schedversion` без расписания** — `{code: 400, message: "no schedule"}`: в контракте у ответа `GET`
   значение обязательно, а версии нет (`schedule_version: null` в `hello`).
3. **Тексты ошибок разбора команды:** `unknown command`, `invalid value`, `bad request`, `unsupported version`.
   В ТЗ есть только `time not synced`, `deadline passed`, `interrupted by reboot`, `schedule changed`, `schedule save failed`.
4. **Энергосбережение без расписания** — нагрев и охлаждение выключены: по §7.3 вне рабочего окна они выключены,
   а окон нет. Так же — день без окна. В существующей прошивке такого случая нет (она переключает только в минуту события).
5. **`hello`** — при каждом подключении, не только после старта (как в `contracts/README.md`).
6. **Ресурс фильтра** — меньший из остатков по литрам и по дням; значения по умолчанию из `unit.h`:
   25 000 л, 365 дней, простой 21 день (`B2`). `filterreset` сбрасывает все три.
7. **`past_state`** всегда `null`, кодов ошибок контроллера нет — до A-27 и RE-4.

Температуры, расход воды и качество связи — правдоподобная модель, а не данные реальных кулеров.

## Проверка

```
pnpm typecheck
pnpm test
```

Тесты: жизненный цикл команд, расписание и CRC32, буфер FW-5 (2 ч и 80 ч обрыва, 1 000 событий, обрыв до подтверждения),
счётчики FW-10 и 20 обрывов питания, сценарии
на 50 устройствах за двое суток (все сообщения — по контрактам), 2 000 устройств за час виртуального времени
и канал MQTT на локальном брокере с обрывом и переподключением.
