## 1. Цель Stage 1

Работающая платформа оператора VENDEN и портал конечного клиента (End User) на **10 реальных
устройствах** по LTE: устройства в реестре и на карте, телеметрия и счётчики идут, алерты срабатывают,
команды доходят и логируются, фильтры прогнозируются.

Обе стороны связи — наши: **прошивка платы связи** в кулере (раздел 4.0) и облачная платформа.
Работа с прошивкой ведётся на реальном устройстве с первых недель.

### 1.1 Пилот сдан, когда

- На пилотных устройствах (10; если SIG поставила меньше — на всех поставленных) стоит наша прошивка платы связи одной версии; устройства подключены по LTE/eSIM
  и стабильно передают heartbeat и телеметрию 7 суток подряд, пропущено не более 1 % кадров.
- Обрыв питания и обрыв LTE не ломают устройство: после восстановления оно само подключается и досылает
  накопленные события (FW-5).
- Дашборд, список, карта, карточка устройства показывают реальные данные этих устройств.
- «Request data now» обновляет данные свежим внеочередным кадром с тем же `cmd_id` в течение 30 с от создания запроса (V-039, §7.3). Замеряем все запросы к онлайн-устройствам и выясняем причину каждого тайм-аута.
- Все команды MQTT к онлайн-устройству имеют общий срок 30 с от создания, включая повторы. В журнале фиксируется итог команды. Для нагрева, охлаждения и общего выключения отдельно измеряем время подтверждения по UART и время получения результата платформой (§7.3, Proposal D-1/D-3).
- Офлайн, ошибка, фильтр, температура вызывают алерты по правилам (раздел 4.10).
- End User видит и управляет только своими кулерами.
- Роли и права работают, действия попадают в журнал аудита.
- Сценарии E2E-01, 02, 03, 04, 06, 07 проходят на реальных устройствах.

## 3. Сквозные решения (из Proposal, раздел 4)

- Azure, регион ЕС; IoT Hub + DPS, X.509 на устройство; встроенный endpoint IoT Hub → обработчики телеметрии
  (отдельных Event Hubs нет); очередь команд и фоновых задач — в PostgreSQL (бизнес-БД);
  PostgreSQL 17 Flexible Server (бизнес) + TimescaleDB на двух ВМ (телеметрия); Azure Managed Redis — состояние устройств,
  heartbeat, сессии; приложения — Azure Container Apps.
- Node.js LTS, TypeScript, NestJS на Fastify, Drizzle; фронтенд React + Vite + Mantine, ECharts, MapLibre + OSM; Refine — админка.
- Мультиарендность через row-level security в PostgreSQL с первого дня (VENDEN — первый арендатор).
- Три среды: dev, staging, prod. Terraform, CI/CD, ручное подтверждение выкладки в prod.
- Протокол: MQTT over TLS, QoS 1, команды с подтверждением на уровне приложения, версионированный payload.
  Телеметрия — один сводный кадр раз в 5 минут (A-10) + события по факту.
- Симулятор устройства — с первого спринта: нагрузку и сценарии, которые на железе не воспроизвести,
  гоняем на нём; основная проверка протокола — на реальном устройстве.
- **Граница прошивки:**
  - **плата связи (ESP32-C3) — наша**: модем LTE, TLS и сертификат устройства, MQTT, протокол, буфер на время
    обрыва, обмен с контроллером кулера, сторожевой таймер, версия прошивки. Наша прошивка заменяет
    существующую прошивку платы и сохраняет её функции (FW-8, FW-10);
  - **контроллер кулера — SIG**: нагрев, охлаждение, пастеризация, датчики, защитные блокировки.
    Его прошивку мы не меняем, команды отдаём через его интерфейс (UART, строки `AT+LOAD`/`AT+PUSH`).
- **Протокол — от существующего, расширяем сами.** Исходная точка — существующая прошивка платы
  (`docs/sig/SS_IOT/`): текстовые команды `GET`/`POST` по BLE и строки `AT+LOAD`/`AT+PUSH` к контроллеру
  (`analysis/BOARD_FIRMWARE.md`). Проверку на устройстве, сервисные команды, коды ошибок и их смысл,
  документацию делаем сами.
- **OTA плата поддерживает** (подтверждено 21.11): загрузчик с обновлением по воздуху закладываем
  с первой версии прошивки, но **по умолчанию обновление по воздуху выключено**; включается настройкой
  устройства по решению SIG (FW-7).
- **Первая установка — по кабелю.** В существующей прошивке flash размечена под одно приложение, разделов OTA нет,
  поэтому нашу прошивку на каждое устройство в первый раз записываем по кабелю (UART0, режим загрузки ESP32-C3);
  дальнейшие обновления — по кабелю или по воздуху (FW-7, FW-9).

### 4.0 Устройство: анализ и прошивка платы связи (MVP-0/1, V-031 — «Key deliverable» ТЗ)

| ID | Что сделать / «готово» |
|---|---|
| RE-1 | **Карта Bluetooth**: BLE-сервис (в существующей прошивке — `0xABF0`), характеристики записи и уведомлений, имя устройства, формат строк `GET`/`POST`. «Готово»: таблица в репозитории, проверена со стенда. |
| RE-2 | **Команды и ответы** — по `docs/sig/cloud_control.c` и таблице команд `docs/sig/commands_sheet.xlsx`: для каждой команды — параметр, диапазон, ответ, состояние («работает», «заглушка», «нет на контроллере», см. `analysis/BOARD_FIRMWARE.md`, раздел 5). Приложение com.cooltouch.app (APK) — только чтобы отметить, какие команды оно реально использует. «Готово»: таблица в репозитории; каждая команда со статусом «работает» отправлена со стенда, действие подтверждено ответом и состоянием кулера. |
| RE-3 | **Интерфейс к контроллеру кулера**: UART, строки `AT+LOAD=<код>:<значение>` (контроллер → плата) и `AT+PUSH=<код>:<значение>` (плата → контроллер). Первый шаг — предпосылки: параметры линии (скорость, уровни), включены ли шифрование flash и secure boot (`espefuse summary`), снимается копия текущей прошивки (`esptool read_flash`) для возврата; копия сверяется со сборкой проекта `docs/sig/SS_IOT/` — та ли версия стоит на устройстве. По плате определяется, к каким выводам ESP32-C3 подключён модем LTE. Затем прослушивание линии через USB-UART: полный перечень строк, которые шлёт контроллер, и реакция на каждую `AT+PUSH`. «Готово»: описание строк и параметров линии в репозитории, проверено на устройстве; копия исходной прошивки сохранена, возврат на неё проверен, результат сверки с проектом записан; подключение модема описано. |
| RE-4 | **Сервисные команды и коды ошибок**: сервисные строки (`AT+TEST`, `AT+TCHCK`, `AT+ACHCK` и найденные в RE-3) и справочник кодов ошибок — битовая маска ошибок платы (нет CO2, ресурс фильтра, простой) и коды контроллера: код, описание, серьёзность, рекомендуемое действие. Отдельно — сигналы пастеризации от контроллера (начало, конец, результат, ошибка) для V-092, V-093, V-118: есть ли они на линии и в каком виде. Источники: исходники, вызов неисправностей на стенде. «Готово»: справочник в репозитории, каждый код проверен на устройстве или помечен «не воспроизведён»; входит в спецификацию протокола. |
| FW-1 | **Запуск платы**: проект ESP-IDF для ESP32-C3 — на основе полного проекта существующей прошивки (`docs/sig/SS_IOT/`, ESP-IDF 5.5); сборка и прошивка с нашего стенда, отладочный вывод, сторожевой таймер, версия прошивки читается. **Бюджет памяти**: таблица разделов flash — два раздела OTA (FW-7), NVS, буферы FW-5 (864 кадра, 1 000 событий); если не помещается — границы FW-5 уменьшаются до помещающихся правкой FW-5 в этом документе (новая версия), и приёмка FW-5 идёт по новым границам. |
| FW-2 | **LTE**: драйвер модема на интерфейсе, найденном в RE-3; регистрация в сети, APN, контроль качества сигнала (RSSI/RSRP), переподключение. Оба UART ESP32-C3 в существующей прошивке заняты (UART0 — контроллер, UART1 — отладочный вывод); если модем на UART1, отладочный вывод переносится в журнал по BLE (после подключения к облаку — и в журнал на платформе), линия к контроллеру и выводы часов (GPIO6/7/10) не меняются. JTAG на такой плате не используется: встроенный USB-JTAG — на тех же GPIO18/19, внешний (GPIO4–7) пересекается с часами. |
| FW-3 | **Безопасность**: закрытый ключ и сертификат X.509 в защищённом хранилище платы (или в защищённой области памяти, если хранилища нет), mTLS к IoT Hub, регистрация через DPS (индивидуальная запись на устройство). Для пилота сертификат записывается на нашем стенде, процедура описана. **Ротация**: до истечения срока прошивка получает новый сертификат по защищённому соединению и регистрируется с ним заново (см. CERT). «Готово»: первичная регистрация, ротация на стенде без выезда, отозванное устройство не подключается и не регистрируется повторно. |
| FW-4 | **MQTT и протокол**: кадр телеметрии раз в 5 минут, события по факту, heartbeat, приём команд, подтверждение и результат, защита от повторного исполнения — по спецификации PRT. |
| FW-5 | **Надёжность**: буфер на время обрыва связи с досылкой после восстановления; переживает обрыв питания; время берётся из сети и не идёт назад. Границы: **телеметрия** — до 72 ч (864 кадра), при переполнении удаляются самые старые кадры; **события** — отдельный буфер до 1 000 событий, при переполнении удаляются самые старые, а после восстановления связи устройство шлёт событие «переполнение буфера» с числом потерянных; **накопительные счётчики** — хранится последнее значение, потеряться не могут; при обрыве питания теряется не больше последнего неотправленного кадра. «Готово» (на устройстве): (1) обрыв LTE 72 ч при ≤ 1 000 событий — ничего не потеряно; (2) обрыв сверх 864 кадров и 1 000 событий — потеряны только самые старые, событие о переполнении пришло с верным числом; (3) 20 обрывов питания подряд — счётчики целы. |
| FW-6 | **Мост к контроллеру**: каждая команда Stage 1 (раздел 4.9) исполняется по таблице соответствия 7.3 — на контроллере строкой `AT+PUSH` (нагрев, охлаждение) или самой платой, как в существующей прошивке (питание, энергосбережение, расписание, сброс фильтра), — и возвращает результат; сброс потребления — операция платформы (7.2), на устройство не уходит. Для нагрева и охлаждения плата формирует успешный MQTT-результат после свежего `AT+LOAD` с запрошенным состоянием (§7.3, п. 7). Телеметрия (нагрев/охлаждение, температуры и уставки, общий расход `WCS`, бутыль, УФ-лампа, газ) собирается из строк `AT+LOAD` по RE-3, остальные поля кадра — из состояния платы (7.3). |
| FW-7 | **Обновление прошивки**: загрузчик с OTA (два образа, откат при неудачном старте) — с первой версии. **По умолчанию обновление по воздуху выключено**: устройство отклоняет его, пока не включена настройка устройства «OTA разрешено». Настройку включает и выключает Admin командой с платформы по решению SIG, каждое изменение — в журнале аудита. Пока OTA выключено, прошивка обновляется по кабелю. Управление OTA из портала SIG (S-010, E2E-10) — Stage 2. «Готово» (на стенде): при выключенной настройке обновление отклонено; при включённой — обновление по воздуху, прерванное обновление и откат. |
| FW-8 | **Совместимость с CoolTouch**: сохраняем имена, синтаксис команд `GET`/`POST` и формат ответов по BLE для текущего приложения CoolTouch и сервисного доступа техника. Разбор и исполнение команд общие для BLE и MQTT (§7.3). «Готово»: команды со статусом «работает» (RE-2) проверены приложением на устройстве с нашей прошивкой. |
| FW-9 | **Выпуск**: версионированная сборка из CI, журнал изменений, версия прошивки читается по BLE и в `hello` (в существующей прошивке — постоянное `100500`); одна сборка на все модели, модель — настройка устройства (в существующей прошивке модель задаётся при сборке). **Инструкция по первой установке по кабелю** на 10 пилотных устройств: подключение к UART0 с отключённой линией к контроллеру, вход в загрузчик (BOOT/GPIO9, EN), сохранение копии исходной прошивки, запись, проверка, возврат кулера в работу. «Готово»: по инструкции прошито устройство на стенде с проверкой FW-10. |
| FW-10 | **Функции существующей прошивки платы сохраняются**: учёт ресурса фильтра (литры, дни, простой) и его сброс, расписание питания, циклическое включение УФ-лампы (UVC) с настраиваемыми интервалами, датчик CO2, PIN и режим аренда/продажа, объём и замена бутыли, энергосбережение, часы, хранение настроек и счётчиков при обрыве питания (перечень — `analysis/BOARD_FIRMWARE.md`, раздел 4). **Исключения**: (1) общий счётчик воды не обнуляется ни одной командой, в том числе `filterreset` и `lastbswap:0`, которые в существующей прошивке его обнуляют (7.2); (2) расписание питания исполняется по правилам 7.3 — в существующей прошивке переключения происходят только в минуту события, начало выходного периода записывается как включение, проверка энергосбережения отключена (`auxilary_devices.c`). «Готово»: каждая функция проверена на стенде до и после замены прошивки с одинаковым результатом, кроме исключений; для (1) — тест: после `filterreset` и `lastbswap:0` общий счётчик не уменьшился; для (2) — тесты: перезагрузка внутри и вне рабочего окна, рабочее окно внутри выходного периода, расписание при выключенном энергосбережении. |

| E2E-06 | Прогноз замены фильтра и список ближайших замен | |
| E2E-07 | Офлайн-алерт → карточка → проверка eSIM → действия техника | |
| E2E-EU | (новый) End User входит, видит только свои кулеры, сбрасывает счётчик, выключает нагрев | |
| E2E-FW | (новый) Устройство с нашей прошивкой: включение → подключение по LTE → телеметрия; обрыв питания и обрыв LTE → само восстанавливается, накопленное досылается; команда из портала исполняется кулером | На реальном устройстве проверяем включение и выключение нагрева и охлаждения. После `ack` без нужного подтверждения UART команда получает `expired` на 30-й секунде. Потеря `ack` вызывает повтор с тем же `cmd_id` без повторного исполнения. Поздняя команда не исполняется, поздний результат сохраняет статус `expired` (§7.3, п. 7). |

В E2E-FW также проверяем `POST power:0` с обоими подтверждениями и с пропуском одного из них. Сверяем замеры UART и платформы по `cmd_id`, в том числе при своевременном подтверждении UART и позднем получении результата платформой. Для расписания проверяем восстановление после перезагрузки, ответ об ошибке при неудачном сохранении и общий дедлайн 30 с для каждого шага обмена.

E2E-05 исключён. E2E-08 и E2E-10 — Stage 2 (OTA плата поддерживает).
E2E-09 — вне Stage 1: требует RMA и аналитики качества, которые Proposal исключил.

### 6.0 Удалённый стенд (первый шаг дорожки «Устройство»)

Агрегаты (почасовые, суточные) — непрерывные агрегаты TimescaleDB поверх Telemetry frame.

**Учёт воды.** `water_total_l` на устройстве никогда не сбрасывается пользователем: это монотонный накопительный счётчик.
- Источник счётчика — по модели, как в существующей прошивке: нижняя бутыль без газированной воды и подключение
  к водопроводу — фактическая выдача (`AT+LOAD=WCS`); верхняя бутыль — объём бутыли, прибавляемый при её установке
  (`BOT`), поэтому потребление у этих моделей считается шагами по одной бутыли; нижняя бутыль с газированной водой —
  источника в существующей прошивке нет, счётчик для неё работает, только если источник найден в RE-3.
  Модель устройства и тип источника видны в карточке устройства рядом с потреблением.
- Потребление за период = разница счётчика на концах периода; сбросы на него не влияют, досланные кадры
  встают на своё время (`ts`).
- «Сброс счётчика потребления» — запись Consumption reset на платформе, а не команда устройству.
  «Потреблено с последнего сброса» = текущий `water_total_l` − точка отсчёта.
- Если счётчик устройства уменьшился (замена платы, сбой) — платформа пишет событие «разрыв счётчика» и считает
  дальше от нового значения, без отрицательного расхода.
- Ресурс фильтра считает платформа: литры с даты установки фильтра по тому же счётчику. Сброс фильтра —
  запись Filter на платформе и команда `POST filterreset:1`: у существующей прошивки платы свой счётчик фильтра
  (литры, дни, простой — FW-10), он сбрасывается вместе с платформенным.
«Готово»: схема в миграциях Drizzle, ER-диаграмма и описание сущностей — в технической документации.

### 7.3 Временный кадр телеметрии и команды

Действует до спецификации PRT: на нём работают симулятор, приём телеметрии, очередь команд и экраны.
После PRT меняется адаптер приёма, а не модель данных 7.2.

Кадр раз в 5 минут, JSON, версия `v: 0`:

| Поле | Тип | Смысл |
|---|---|---|
| `v`, `device_id`, `ts`, `seq` | int, string, ISO-8601, int | версия кадра, устройство, время на устройстве, номер кадра |
| `cmd_id` | string или null | у внеочередного кадра по `GET all` — команда, по которой он отправлен |
| `t_hot`, `t_cold` | °C, число или null | факт горячей и холодной воды (`AT+LOAD=HTT`, `CTT`) |
| `t_hot_set`, `t_cold_set` | °C, число или null | уставки контроллера, только чтение (`HST`, `CST`) |
| `heat_on`, `cool_on` | bool | нагрев и охлаждение работают сейчас (`HTR`, `CLR`) |
| `heat_enabled`, `cool_enabled` | bool | нагрев и охлаждение разрешены — флаги платы `HOT_ENABLE`/`COLD_ENABLE`, задаются `POST hottank`/`coldtank` (`GET hottank`/`coldtank` отдают не разрешение, а фактическое состояние) |
| `power_on` | bool | общий вкл/выкл нагрева и охлаждения (`power`) |
| `energy_saving` | bool | работа по расписанию включена (`energysaving`) |
| `water_total_l` | число, накопительное | общий объём (P-02), счётчик платы; источник зависит от модели — 7.2 «Учёт воды» |
| `bottle_present` | bool или null | бутыль установлена (`BOT`) — у моделей с верхней бутылью (в существующей прошивке `BOT` обрабатывается только для них); null — у остальных моделей, пока RE-3 не найдёт для них сигнал |
| `uvc_on` | bool | УФ-лампа включена (`UVC`) |
| `co2_ok` | bool или null | газ есть (`GAS` / датчик CO2); null — модель без газированной воды |
| `filter_left_pct`, `filter_used_l`, `filter_days`, `idle_days` | %, литры, дни, дни | ресурс фильтра и простой по счётчикам платы (`filterleft`, `filtertime`, `nwutime`) |
| `past_state` | idle/running/done/error или null | состояние пастеризации; null, пока контроллер не передаёт сигналы (A-27) |
| `errors` | массив кодов | активные ошибки: биты платы (`B1` — ресурс фильтра исчерпан, `B2` — превышен простой, `B3` — нет CO2) и коды контроллера по RE-4 |
| `rssi`, `rsrp`, `rsrq`, `sinr`, `operator`, `roaming` | числа, string, bool | качество связи |
| `fw`, `hw` | string | версия прошивки и ревизия железа (в первом кадре после старта) |

События — отдельными сообщениями по факту, общий формат:
`{v, device_id, seq, ts, type, code?, data?}` — `ts` — время возникновения на устройстве, `seq` — общий для кадров
и событий номер, растёт монотонно и сохраняется при перезагрузке.

| `type` | `code` / `data` |
|---|---|
| `error_raised`, `error_cleared` | код ошибки |
| `past_started` | инициатор: auto / manual, пользователь — если известен |
| `past_finished` | `started_ts`, результат ok / error, код ошибки |
| `bottle_removed`, `bottle_installed` | время; при установке — литры с прошлой замены (модели с верхней бутылью) |
| `reboot` | причина: питание / сторожевой таймер / обновление |
| `buffer_overflow` | число потерянных кадров и событий |
| `schedule_applied` | версия расписания; источник: `platform` или `local` (изменено по Bluetooth — тогда с содержимым расписания) |

Повторы: платформа принимает сообщение один раз по паре (`device_id`, `seq`); повторная доставка
(QoS 1, досылка после обрыва) отбрасывается без ошибки. Порядок восстанавливается по `seq`, время — по `ts`.

Heartbeat — раз в 60 с: `{v, device_id, ts}`.

При старте устройство шлёт `hello`: `fw`, `hw`, модель (`model` — тип установки воды, исполнение, наличие газированной воды),
версия действующего расписания, состояние настройки OTA (`ota_allowed`).

**Команды и ответы по BLE и MQTT**

Для совместимости с текущим приложением CoolTouch сохраняем существующие команды BLE `GET <параметр>` и `POST <параметр>:<значение>`. По BLE приложение отправляет команду как текстовую строку. По MQTT платформа передаёт ту же строку в поле `cmd` для команд из таблицы ниже. Прошивка использует общий разбор команд и общую логику исполнения для обоих каналов (FW-6, FW-8).

Ответ зависит от канала. По BLE плата возвращает текстовый ответ в формате, который ожидает CoolTouch (`200 …` или `400 message:…`). Для MQTT действуют следующие правила.

- Платформа отправляет на устройство `{v, cmd_id, deadline_at, cmd: "POST hottank:1"}`. `deadline_at` (ISO-8601 UTC) задаёт общий срок команды. Повторы используют тот же срок.
- Устройство отправляет платформе `{v, cmd_id, ack}` сразу после приёма. `ack` подтверждает только приём команды платой. Для `GET all` итогом служит внеочередной кадр телеметрии с тем же `cmd_id`. Остальные команды возвращают `{v, cmd_id, result}`, где `200 …` означает `success`, а `400 …` означает `error`. Для нагрева, охлаждения и общего выключения действуют условия п. 7. Результат записывается в журнал команды.

Команды Stage 1 (платформа отправляет только их; остальные команды существующей прошивки — `serial`, `datetime`,
`factoryreset`, `pin` и др. — с платформы не уходят, API их отклоняет):

| Действие | Команда | Примечание |
|---|---|---|
| Запросить данные сейчас (V-101) | `GET all` | Плата формирует свежий внеочередной кадр по схеме §7.3 и отправляет его по MQTT с тем же `cmd_id`. Платформа обновляет данные из кадра и фиксирует итоговый статус запроса в журнале команд по правилу 6 ниже. |
| Нагрев вкл/выкл (V-103) | `POST hottank:0/1` | При включённом питании плата управляет нагревом через `AT+PUSH=HTR`. Для успеха контроллер должен подтвердить запрошенное состояние через `AT+LOAD=HTR` в пределах срока команды (п. 7). |
| Охлаждение вкл/выкл (V-104) | `POST coldtank:0/1` | При включённом питании плата управляет охлаждением через `AT+PUSH=CLR`. Для успеха контроллер должен подтвердить запрошенное состояние через `AT+LOAD=CLR` в пределах срока команды (п. 7). |
| Питание — общий вкл/выкл нагрева и охлаждения (V-105) | `POST power:0/1` | Для выключения плата использует `AT+PUSH=HTR:0` и `AT+PUSH=CLR:0`. `POST power:0` получает `success` после обоих свежих подтверждений по UART (`AT+LOAD=HTR:0` и `AT+LOAD=CLR:0`) в пределах общего срока команды (п. 7). |
| Энергосбережение — работа по расписанию (V-105) | `POST energysaving:0/1` | |
| Расписание (V-106) | `POST autopowerscheduling:<расписание>` | Плата возвращает `200 ok` после успешного сохранения расписания в энергонезависимой памяти. Формат и порядок отправки описаны ниже. |
| Сброс фильтра (V-089) | `POST filterreset:1` | без обнуления общего счётчика воды (FW-10) |
| Самодиагностика (V-107) | `POST selftest:1` → `200 selftest:<проверка>=ok|fail;…` | **новая** — нашей прошивки |
| Версия расписания | `GET schedversion` / `POST schedversion:<номер>,<CRC32 часового пояса и расписания>` | **новая**; `local:<время>` — изменено на месте |
| Часовой пояс адреса | `GET timezone` / `POST timezone:<IANA>` | **новая**; по умолчанию `Europe/Riga` |
| Разрешить OTA (FW-7, только Admin) | `GET otaallowed` / `POST otaallowed:0/1` | **новая** |

Новые команды также доступны по BLE через общий обработчик.

Полный ответ `200 all;…` используется локально по Bluetooth. Плата исключает `pin1`, `pin2` и их значения из всех отправляемых в облако данных, включая повторные доставки и отладочные логи (FW-2).

Сброс потребления — не команда (см. 7.2). Уставки температуры, `dsp`/`cdsp`, стерилизация по расписанию и прочие
заглушки существующей прошивки (`analysis/BOARD_FIRMWARE.md`, раздел 5) в команды Stage 1 не входят.

**Расписание.**
- Источник истины — платформа; хранится в Setting устройства с номером версии.
- Формат — строка `autopowerscheduling` существующей прошивки: `w<день 1..7>,<с HH:MM>,<до HH:MM>;` — до одного
  рабочего окна на день недели (время — местное по `timezone`), `f<0..32>,<начало>,<конец>;` — до 33 выходных периодов
  (Unix-время). В примере выходной период длится с 00:00 6 марта до 00:00 8 марта 2027 года по `Europe/Riga`.
  `POST autopowerscheduling:w1,08:30,18:30;w2,08:30,18:30;f0,1804284000,1804456800;`
  Вне рабочего окна и в выходной период нагрев и охлаждение выключены. Выходной период имеет приоритет перед рабочим окном. Расписание действует, только когда включено
  энергосбережение (`energy_saving`). Плата вычисляет нужное состояние по расписанию в каждый момент, поэтому
  после перезагрузки или пропущенной минуты состояние восстанавливается. Это изменение относительно
  существующей прошивки (исключение FW-10).
- Исполняет прошивка платы связи локально, по часам платы, сверенным со временем сети, — расписание работает и без связи.
- Устройство сообщает версию действующего расписания в `hello` и событием `schedule_applied`; при расхождении
  с платформой платформа повторно шлёт расписание (`schedversion`, `timezone`, `autopowerscheduling`). Портал всегда показывает расписание из платформы
  и отметку «применено на устройстве / ожидает».
- **Сохранение на плате.** Ответ `200 ok` на `POST autopowerscheduling` подтверждает, что расписание записано в энергонезависимую память и будет восстановлено после перезагрузки. При ошибке записи плата возвращает `400 message:schedule save failed` и продолжает использовать последнее сохранённое расписание.
- **Отправка с платформы:** `POST timezone:<IANA>`, затем `POST autopowerscheduling:<расписание>`, затем
  `POST schedversion:<номер>,<CRC32 строки «<timezone>|<расписание>»>`; каждая следующая — только после ответа `200 ok`
  на предыдущую. У каждой из этих команд свой 30-секундный срок для онлайн-устройства. Ошибка или `expired` на любом шаге останавливает отправку, расписание остаётся «ожидает»
  и отправляется заново всей последовательностью по правилу расхождения версий. Любая запись `autopowerscheduling` (по LTE или Bluetooth)
  сначала помечает расписание версией `local:<время изменения>`; номер платформы устройство принимает только
  командой `schedversion` и только если CRC32 совпадает с действующими часовым поясом и расписанием; иначе — `400 message:schedule changed`
  (расписание успели изменить на месте), номер не присваивается. Если `schedversion` не дошла, устройство сообщает локальную версию
  с содержимым; совпадает с отправленным — платформа повторяет `schedversion`, иначе — изменение на месте (ниже).
  Отметка «применено» ставится только по номеру платформы.
- **Изменение на месте.** Расписание, изменённое через Bluetooth-приложение, устройство применяет, помечает
  версией `local:<время изменения>` (`schedversion`) и сообщает событием `schedule_applied` с источником `local`
  и содержимым; пока версия локальная, `hello` тоже несёт содержимое расписания. Платформа сохраняет его новой
  своей версией с отметкой «изменено на месте» и записью в журнале аудита и шлёт `POST schedversion:<новый номер>,<CRC32 часового пояса и этого содержимого>` —
  устройство переходит на номер платформы без изменения расписания.
  Локальную версию платформа своим расписанием не перезаписывает. Если расписание менялось и на месте,
  и на платформе, пока устройство было без связи, действует более позднее изменение; другое остаётся в истории версий.

**Жизненный цикл команды** (V-037):

Пункты 1–5 относятся ко всем командам MQTT. Пункты 6 и 7 уточняют условия завершения `GET all` и команд, требующих подтверждения по UART.

1. `pending` — команда создана и ждёт отправки. Для любой команды к онлайн-устройству срок **30 с от создания** включает очередь, доставку, повторы, исполнение и получение результата. Для `GET all`, `POST hottank`, `POST coldtank` и `POST power:0` срок отсчитывается от создания и при офлайне. Остальные команды, созданные при офлайне, могут ждать связи в очереди до 10 мин. Если связь восстановилась в срок, их 30-секундное окно начинается при первой отправке. Если связь так и не появилась, команда получает `expired`.
2. `sent` — команда отправлена. Пока платформа ждёт `ack` и команда не завершена, повторы проходят через 10 и 20 с от начала 30-секундного окна с теми же `cmd_id` и `deadline_at`. Плата проверяет дедлайн перед началом исполнения и перед отправкой по UART. Команда, доставленная после дедлайна, не исполняется.
3. `ack` означает приём команды платой. Платформа прекращает повторы и ждёт итог до исходного `deadline_at`.
4. `success` / `error` — по итоговому `result` с тем же `cmd_id`, полученному платформой в пределах срока. Для `GET all` итог определяется по п. 6. По истечении срока без итога платформа ставит `expired`. Поздний `result` записывается в журнал команды с отметкой «поздний», статус остаётся `expired`. Время ожидания результата измеряет платформа от начала 30-секундного окна.
5. Устройство хранит последние 100 `cmd_id` со статусом (принята / выполняется / завершена + результат, если предусмотрен)
   в энергонезависимой памяти; `cmd_id` записывается **до** начала исполнения, поэтому список переживает перезагрузку.
   При повторе с известным `cmd_id` устройство возвращает `ack` без повторного исполнения. Для завершённой команды оно также повторяет прежний `result`, если он предусмотрен. Если перезагрузка прервала исполнение, команда не возобновляется.
   Для команд с `result` устройство сообщает `400 message:interrupted by reboot`.
6. Для `GET all` платформа ставит `success`, когда в пределах общего срока получает свежий внеочередной кадр, сформированный по запросу с тем же `cmd_id`, и обновляет данные устройства. При повторе уже обработанного запроса плата повторно отправляет исходный кадр, если он ещё доступен, с теми же `cmd_id` и `seq`.
   Если нужный кадр не применён к дедлайну, платформа ставит `expired` и показывает «Свежие данные не получены за 30 с». Поздний кадр сохраняется в истории с дедупликацией по `seq`, статус запроса остаётся `expired`.
7. Для `POST hottank`, `POST coldtank` и `POST power:0` успешный итог зависит от подтверждения контроллера по UART.
   Плата обрабатывает по одной активной команде на нагрев и на охлаждение. Для `POST hottank` или `POST coldtank` успешный `result` с тем же `cmd_id` формируется после свежего `AT+LOAD=HTR` или `AT+LOAD=CLR` со значением, запрошенным командой. Для `POST power:0` плата ждёт оба свежих подтверждения (`AT+LOAD=HTR:0` и `AT+LOAD=CLR:0`) и выполняет общее выключение отдельно от других команд нагрева и охлаждения.
   При изменении состояния плата ждёт подтверждение после отправки `AT+PUSH` для текущей команды. Если состояние уже установлено, плата подтверждает его свежим сообщением контроллера. При явной ошибке платформа ставит `error` по полученному результату.
   На плате отдельно измеряется время от первой отправки по UART до последнего требуемого подтверждения. Если состояние уже установлено, отсчёт начинается с проверки актуального состояния. Оба замера связываются по `cmd_id`. Итоговый статус по дедлайну определяется временем получения результата платформой. Плата прекращает попытки отправки этой команды по UART по истечении срока и учитывает последующие сообщения контроллера в телеметрии.

### 7.5 Портал End User

- **Учётная запись** создаёт оператор (Admin или Dispatcher) в карточке клиента: e-mail → приглашение с ссылкой
  на 72 ч → End User задаёт пароль. Самостоятельной регистрации нет.
- **Привязка — к клиенту, не к устройству:** End User видит все кулеры своего клиента по всем адресам.
  У одного клиента может быть несколько End User; один End User может быть привязан к нескольким клиентам
  (переключатель вверху).
- **Экраны** (под телефон, затем планшет и компьютер):
  1. Вход, восстановление пароля, выбор языка (LV, RU, EN, ET, LT; по умолчанию — язык браузера).
  2. Мои кулеры: адрес, этаж и место, статус (работает / нет связи / нужна замена фильтра), ресурс фильтра в %.
  3. Карточка кулера: потребление за день/неделю/месяц/свой период (график и итог), ресурс фильтра, состояние нагрева и охлаждения.
  4. Управление: питание, энергосбережение, расписание, нагрев и охлаждение вкл/выкл; результат команды показывается.
  5. Сбросы: ресурс фильтра, счётчик потребления (точка отсчёта, 7.2) — с двойным подтверждением; оператор видит сброс в журнале
     устройства, фильтр получает новую дату установки.
  6. Профиль: имя, пароль, язык.
- **Чего End User не видит:** журналы команд и ошибок, eSIM, технические параметры, других клиентов.
- **Блокировка:** оператор блокирует учётную запись — сессии End User завершаются сразу.
- «Готово»: E2E-EU; все экраны на английском и на тех из LV, RU, ET, LT, переводы которых SIG/VENDEN передали до 31.01.2027 (язык без перевода принимается отдельно после его передачи); тест «чужой кулер не открывается по прямой ссылке».
