# api

REST API порталов оператора и End User (NestJS на Fastify, Drizzle). Контракт API — [`contracts/openapi`](../../contracts/openapi/).
Схема БД `app` — здесь.

Дорожка: **Платформа**. ТЗ — [`doc/STAGE1_SPEC.md`](../../doc/STAGE1_SPEC.md), §3.1, §6.3, §7.2.

## Схема БД `app`

- [`src/db/schema.ts`](src/db/schema.ts) — таблицы по модели §7.2 (Drizzle); миграция `drizzle/0000_init.sql`
  генерируется из неё: `pnpm db:generate`.
- [`drizzle/0001_contract.sql`](drizzle/0001_contract.sql) — пишется руками: роли `app_api` и `app_device`, RLS по
  арендатору (P-07), только добавление в аудит и историю устройства, значения по умолчанию §7.4, вход до выбора
  арендатора и объекты для дорожки «Устройство» ([`contracts/db`](../../contracts/db/)).
- Применить: `DATABASE_URL=… pnpm db:migrate` (роль-владелец схемы).

Сущности и ER-диаграмма — [`doc/db-app.md`](../../doc/db-app.md).

**Как работает изоляция.** Службы Платформы работают под ролью `app_api` и в начале каждой транзакции ставят
арендатора: `select set_config('app.tenant_id', '<uuid>', true)`. Без этого не видна ни одна строка. Ссылки между
сущностями — составными ключами `(tenant_id, id)`: сослаться на чужое устройство, клиента или пользователя нельзя,
адрес устройства — только его клиента. Вход ищет пользователя, сессию и токен до выбора арендатора функциями
`app.auth_lookup_email`, `app.auth_lookup_session`, `app.auth_lookup_token`. Запрос SIG Administrator (вне арендатора) —
`set_config('app.scope', 'global', true)`: видны его строки с пустым `tenant_id` и можно создать арендатора.
Ограничение End User «только свои кулеры» — в API (по `end_user_access`), не в RLS.

**Расписание** пишется только функциями: `app.schedule_store_platform` (API) и `app.schedule_store_local`
(дорожка «Устройство»). Обе берут блокировку строки устройства — номера версий не пересекаются — и проверяют расписание
(одно окно на день, уникальные номера выходных, начало < конца) и часовой пояс IANA.

**Чего в `app` нет.** Кадры, события, агрегаты, команды и алерты — схема `telemetry` дорожки «Устройство» (§6.3).
Там же то, что сообщает само устройство или выпускает `provisioning`: версия прошивки, last seen, тех. состояние,
отпечаток сертификата. API берёт их у дорожки «Устройство» и показывает в карточке.

## Проверка

```
docker run -d --name icooler-pg -e POSTGRES_PASSWORD=pg -p 127.0.0.1:55432:5432 postgres:17.6
DATABASE_URL=postgres://postgres:pg@127.0.0.1:55432/postgres pnpm test
```

Тест создаёт временную базу, применяет миграции с нуля и проверяет: RLS у каждой таблицы с `tenant_id` (и у сессий),
изоляцию арендаторов, ссылки только внутри арендатора, режим SIG Administrator, логическое удаление и снятие
переопределения настройки, только добавление в аудит, вход до выбора арендатора, права `app_device` (только объекты
контракта), `audit_append`, `schedule_store_local` (повтор события, не дошедший `schedversion`, конфликт изменений),
параллельную запись версий в обоих порядках, проверку расписания и пояса и совпадение базы с
[`contracts/db/app-interface.json`](../../contracts/db/app-interface.json). Каждая защита проверена порчей миграции.

## Решения, которых нет в ТЗ (на согласование)

1. **Действующая версия расписания** — с наибольшим временем изменения, а не номером: так выполняется правило §7.3
   «действует более позднее изменение, другое остаётся в истории». Номер версии только растёт.
2. **`schedule_store_local` принимает и часовой пояс** (`p_timezone`, необязательный): в Bluetooth-приложении его тоже
   можно изменить, а CRC в `schedversion` считается от пояса и расписания.
3. **Одна роль на пользователя** в Stage 1 (`role_assignment` с ключом `user_id`).
4. **Тех. состояние, last seen, прошивка, отпечаток сертификата** — не в `app`: их пишет дорожка «Устройство», а
   писать в `app` она может только через функции контракта (§6.3).
5. **Сессии и токены входа** — под RLS по арендатору; до выбора арендатора — только функции поиска; хранится хеш.
6. **Совпадение с действующей версией** при `schedule_store_local` — не изменение на месте, а не дошедший
   `schedversion`: новой версии нет, dispatcher повторяет `schedversion` (§7.3).
7. **Снять переопределение настройки** — удалить строку `setting`; это единственное физическое удаление в `app`.
