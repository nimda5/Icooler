# api

REST API порталов оператора и End User (NestJS на Fastify, Drizzle). Контракт API — [`contracts/openapi`](../../contracts/openapi/).
Схема БД `app` — здесь.

Дорожка: **Платформа**. ТЗ — [`doc/STAGE1_SPEC.md`](../../doc/STAGE1_SPEC.md), §3.1, §6.3, §7.2.

## Сервис

NestJS 11 на Fastify, `/api/v1`. Сейчас реализованы вход и учётные записи (§4.1, задача #27): операции тегов
`auth`, `profile`, `tenants`, `users`, `end-users`, журнал аудита `GET /audit-log`, настройки V-006
(`/settings`, `/devices/{id}/settings`), клиенты, адреса и контакты (§4.3), реестр устройств (§4.2) и карта (V-025)
контракта
[`contracts/openapi`](../../contracts/openapi/openapi.yaml).

```
pnpm build
DATABASE_URL=… CSRF_SECRET=… pnpm start      # COOKIE_SECURE=false — только для разработки по http
```

`TRUST_PROXY_HOPS` — сколько прокси перед сервисом (Application Gateway — 1). По умолчанию 0: `X-Forwarded-For`
не учитывается, иначе клиент подставит любой IP, обойдёт лимиты и запишет чужой адрес в аудит.

**Маршруты и права — из контракта.** Обработчик объявляется `@Op('operationId', <код>)`: метод и путь берутся из
OpenAPI, права — из `x-roles` (матрица §7.1), тело проверяется той же JSON Schema, что в контракте. Разойтись коду и
OpenAPI негде; тест проверяет, что каждый обработчик есть в контракте.

Каждый запрос проходит `ApiGuard` (`src/http/guard.ts`):
1. лимиты §7.4: вход — 10 в минуту с IP, восстановление пароля — 3 в час на e-mail и 20 в час с IP, API оператора — 600 в минуту на пользователя, End User — 120 в минуту на пользователя и 300 с IP;
2. сессия — cookie `session` (HttpOnly, Secure, SameSite=Strict); в БД — только sha256 токена;
3. роль по `x-roles` — иначе `403`;
4. `X-CSRF-Token` у изменяющих запросов — HMAC от сессии, выдаётся при входе;
5. параметры запроса и тело — по схемам контракта, иначе `422` с полями.

Дальше обработчик работает в транзакции под ролью `app_api` с арендатором пользователя (RLS): объект другого
арендатора — `404`. Каждое изменение пишется в аудит в той же транзакции.

**Вход** (`src/modules/auth.controller.ts`): неверный пароль и неизвестный e-mail — одинаковый `401` (scrypt
выполняется в обоих случаях); 5 неудач подряд — блокировка входа на 15 мин (`423`); неудача фиксируется (счётчик,
аудит) — транзакция коммитится до ответа. Восстановление пароля и приглашение — одноразовые токены (1 ч / 72 ч).

Вход, сброс пароля, приглашение, смена пароля и действия оператора над учётной записью идут **под блокировкой строки
пользователя**: пароль проверяется по тому хешу, что под блокировкой; приглашение не снимает блокировку, выставленную
оператором; при смене или сбросе пароля прочие ссылки сброса гаснут, из двух одновременных ссылок срабатывает одна.
Блокировка, удаление, смена роли и отвязка End User от клиента завершают сессии сразу.

**Настройки** (`src/modules/settings.controller.ts`, V-006, §7.4): пороги офлайна, алертов температуры, фильтра,
список ближайших замен, окно прогноза. Ключи и границы — из схем `Settings` / `SettingsWrite` контракта. Значение
наследуется платформа → арендатор → устройство; в ответе у каждого ключа — откуда оно (`level`). `null` снимает
переопределение своего уровня. Изменения одного уровня идут по очереди (блокировка арендатора или устройства), в аудит —
изменённые ключи до и после.

**Клиенты и устройства** (`src/modules/clients.controller.ts`, `devices.controller.ts`):
- клиенты, адреса, контакты; карточка клиента — с адресами, контактами и его кулерами (V-021…V-024); удаление —
  логическое, клиент или адрес с устройствами — `409`, вместе с клиентом гаснут его адреса, контакты и доступ End User;
- устройства: создание, изменение, уникальность V-011 (серийник — у арендатора, Device ID и IMEI — во всей платформе,
  ответ «занято» без раскрытия чьё — функция `app.device_identity_taken`), перенос к клиенту и адресу, статус
  жизненного цикла, аренда/покупка — с историей (V-013, V-014, P-09);
- список с поиском, фильтрами и сортировкой (`created_at`, `serial`, `device_id`, `client_name`), страницы по курсору;
- карта: устройства с координатами адреса в рамке, кластеры на сервере по сетке масштаба; на крупном масштабе и на
  одном адресе — отдельные маркеры (несколько кулеров на адресе различимы, P-05).

**Состояние устройства** (online, тех. состояние, last seen, прошивка, ресурс фильтра, алерты) пишет дорожка
«Устройство» (`ingest`). Пока его нет, источник `src/telemetry.ts` отвечает «ни разу не выходило на связь»: `offline`,
серый цвет на карте, алертов нет. Фильтры по этим полям считаются от тех же значений — ответ согласован. С появлением
`ingest` меняется только источник.

«Забыли пароль» у приглашённого, который ещё не задал пароль, присылает новое приглашение (прежнее гаснет):
так восстанавливается учётная запись, письмо с приглашением которой потерялось, в том числе первый Admin арендатора.

**Письма** уходят после коммита: откат не оставит у получателя нерабочую ссылку, а сбой почтовой службы не ломает
приглашение (ошибка — в журнал). Восстановление пароля отвечает `202` сразу, токен и письмо делаются в фоне: по
времени ответа и ошибкам доставки нельзя узнать, есть ли такая учётная запись.

## Схема БД `app`

- [`src/db/schema.ts`](src/db/schema.ts) — таблицы по модели §7.2 (Drizzle); миграция `drizzle/0000_init.sql`
  генерируется из неё: `pnpm db:generate`.
- [`drizzle/0001_contract.sql`](drizzle/0001_contract.sql) — пишется руками: роли `app_api` и `app_device`, RLS по
  арендатору (P-07), только добавление в аудит и историю устройства, значения по умолчанию §7.4, вход до выбора
  арендатора и объекты для дорожки «Устройство» ([`contracts/db`](../../contracts/db/)).
- Применить: `DATABASE_URL=… pnpm db:migrate` (роль-владелец схемы).

Сущности и ER-диаграмма — [`doc/db-app.md`](../../doc/db-app.md).

**Как работает изоляция.** Службы Платформы работают под ролью `app_api` и в начале каждой транзакции ставят
арендатора: `select set_config('app.tenant_id', '<uuid>', true)`. Без этого не видна ни одна строка. Ссылки между
сущностями — составными ключами `(tenant_id, id)`: сослаться на чужое устройство, клиента или пользователя нельзя,
адрес устройства — только его клиента. Вход ищет пользователя, сессию и токен до выбора арендатора функциями
`app.auth_lookup_email`, `app.auth_lookup_session`, `app.auth_lookup_token`. Запрос SIG Administrator (вне арендатора) —
`set_config('app.scope', 'global', true)`: видны его строки с пустым `tenant_id` и можно создать арендатора.
Ограничение End User «только свои кулеры» — в API (по `end_user_access`), не в RLS.

**Расписание** пишется только функциями: `app.schedule_store_platform` (API) и `app.schedule_store_local`
(дорожка «Устройство»). Обе берут блокировку строки устройства — номера версий не пересекаются — и проверяют расписание
(одно окно на день, уникальные номера выходных, начало < конца) и часовой пояс IANA.

**Чего в `app` нет.** Кадры, события, агрегаты, команды и алерты — схема `telemetry` дорожки «Устройство» (§6.3).
Там же то, что сообщает само устройство или выпускает `provisioning`: версия прошивки, last seen, тех. состояние,
отпечаток сертификата. API берёт их у дорожки «Устройство» и показывает в карточке.

## Проверка

```
docker run -d --name icooler-pg -e POSTGRES_PASSWORD=pg -p 127.0.0.1:55432:5432 postgres:17.6
DATABASE_URL=postgres://postgres:pg@127.0.0.1:55432/postgres pnpm test
```

Тест создаёт временную базу, применяет миграции с нуля и проверяет: RLS у каждой таблицы с `tenant_id` (и у сессий),
изоляцию арендаторов, ссылки только внутри арендатора, режим SIG Administrator, логическое удаление и снятие
переопределения настройки, только добавление в аудит, вход до выбора арендатора, права `app_device` (только объекты
контракта), `audit_append`, `schedule_store_local` (повтор события, не дошедший `schedversion`, конфликт изменений),
параллельную запись версий в обоих порядках, проверку расписания и пояса и совпадение базы с
[`contracts/db/app-interface.json`](../../contracts/db/app-interface.json). Каждая защита проверена порчей миграции.

## Решения, которых нет в ТЗ (на согласование)

Сервис:
- **Сессия End User без «запомнить меня»** — 12 ч, как у оператора; с ним — 30 дней (§7.4).
- **Свою роль изменить, себя заблокировать или удалить нельзя** (`409`) — чтобы арендатор не остался без Admin.
- **Повторный e-mail при приглашении — `409`**: e-mail уникален во всей платформе (вход один для всех
  арендаторов), поэтому Admin узнаёт, что адрес занят, даже если он у другого арендатора.
- **Лимиты запросов — в памяти процесса.** При нескольких репликах `api` — перенести в Redis (интерфейс тот же),
  иначе лимит считается на реплику.
- **Письма** — интерфейс `Mailer`; отправка через почтовую службу Azure — вместе с `infra/core`. Очередь писем
  в памяти процесса: при падении процесса между коммитом и отправкой письмо теряется (повтор — новым приглашением или
  запросом). Надёжная очередь (outbox) — когда появится `jobs-app`.
- **Критичный порог фильтра не выше порога предупреждения** — иначе `422`, в том числе если новое значение
  арендатора сделает так у устройства с переопределением.
- **`ota_allowed` и `timezone` — не настройки V-006**: разрешение OTA меняется командой (`/actions/ota-allowed`, FW-7),
  часовой пояс — у адреса и расписания (§7.3). В таблице настроек они есть только как значения по умолчанию для
  дорожки «Устройство» (`v_device_setting`).
- **Геокодирование адреса** (V-022) — Azure Maps в подписке проекта (ресурсы в ЕС), ключ `AZURE_MAPS_KEY` — с
  `infra/core`. Без ключа или если адрес не нашёлся — адрес сохраняется без координат и на карте не виден; координаты
  можно задать вручную (`coords_source: manual`). Геокодирование — до транзакции, таймаут 3 с.
- **`ota_allowed` в карточке** — по последнему `hello` устройства (дорожка «Устройство»); до телеметрии — `null`.
- **Фильтр `model`** — по SKU или типу установки воды (`bottle_top`, `bottle_bottom`, `mains`).
- **Сортировка списка устройств** — только по `created_at`, `serial`, `device_id`, `client_name`; другие — `422`.
- **Кластеры карты** — сетка в 1/4 размера тайла масштаба, считается в SQL без лимита; с масштаба 17 и для точек одного
  адреса — отдельные маркеры.
- **Курсор списка устройств** — поле сортировки и id последней строки; значение сортировки берётся из БД.
- **`409` у пользователей** — своя роль, себя заблокировать или удалить, разблокировать незаблокированного; добавлено
  в контракт.
- **Пароль** — от 12 символов (схема контракта), хеш — scrypt (N = 2¹⁵, r = 8, p = 1).

Схема БД:

1. **Действующая версия расписания** — с наибольшим временем изменения, а не номером: так выполняется правило §7.3
   «действует более позднее изменение, другое остаётся в истории». Номер версии только растёт.
2. **`schedule_store_local` принимает и часовой пояс** (`p_timezone`, необязательный): в Bluetooth-приложении его тоже
   можно изменить, а CRC в `schedversion` считается от пояса и расписания.
3. **Одна роль на пользователя** в Stage 1 (`role_assignment` с ключом `user_id`).
4. **Тех. состояние, last seen, прошивка, отпечаток сертификата** — не в `app`: их пишет дорожка «Устройство», а
   писать в `app` она может только через функции контракта (§6.3).
5. **Сессии и токены входа** — под RLS по арендатору; до выбора арендатора — только функции поиска; хранится хеш.
6. **Совпадение с действующей версией** при `schedule_store_local` — не изменение на месте, а не дошедший
   `schedversion`: новой версии нет, dispatcher повторяет `schedversion` (§7.3).
7. **Снять переопределение настройки** — удалить строку `setting`; это единственное физическое удаление в `app`.
